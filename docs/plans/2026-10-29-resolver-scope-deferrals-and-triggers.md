# Resolver Scope Deferrals and Reopening Triggers — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record — in one canonical decision document — which resolver capabilities Oneiric deliberately does **not** adopt, and the precise trigger that would reopen each one, so that deferrals are not re-litigated from scratch in every review cycle.

**Architecture:** This plan produces a decision record, not runtime code. The single piece of runtime-adjacent work is a **trigger detector**: a test that fails the moment a deferred capability's precondition becomes true, so the deferral surfaces automatically instead of waiting to be remembered. Everything else is documentation that must survive future refactors of the resolver.

**Tech Stack:** Python 3.14, Pydantic v2, pytest. No new dependencies.

**Spec:** `docs/RESOLUTION_LAYER_SPEC.md` (role: `canonical`, status: `active`, topic: `resolver`)

## Global Constraints

- The deliverable is a **decision record**, not a design proposal. Each entry states a decision, its rationale, and its reopening trigger — no estimates, no comparison essays.
- Deferrals must name an **observable trigger**, not a vague condition. "When we need it" is not a trigger. "When `CandidateSource` gains a fifth member" is a trigger.
- Rejected items stay rejected with a rationale. Do not park a rejection as a deferral.
- The decision record must not contradict `docs/RESOLUTION_LAYER_SPEC.md`. Where the two overlap, the spec states *what* the resolver does; the decision record states *what it will not become*.
- Oneiric's existing decisions are numbered `0001`–`0003` in `docs/decisions/`. The new record is `0004`.
- No changes to `oneiric/core/resolution.py` behavior. The only test added is a cardinality guard.

## Review Focus

1. **A new `CandidateSource` member.** This is the provider-protocol trigger. A cardinality guard must fail loudly rather than silently expanding the enum. Covered by Task 2.
2. **A future request to "resolve these three components together."** That is the set-resolution trigger. The decision record must make the cost explicit so the request is scoped rather than waved through. Documented in Task 1.
3. **A config file that wants to name an action kit.** That is the interpolation trigger, and it is a *security* trigger because `CandidateSource.REMOTE_MANIFEST` exists — a fetched manifest must never be able to invoke registered callables. Documented in Task 1.
4. **A second positioning mechanism appearing in the wild.** If any plugin author starts wanting `tryfirst`/`trylast`, that is the moment to revisit decision 5 — but it must be revisited as a *replacement* for `priority`, not an addition to it. Documented in Task 1.

Title: `# ADR 0004: Resolver Scope Boundaries and Reopening Triggers`.

- [ ] **Step 2: Write the Context section**

State the situation in three sentences: Oneiric's resolver is a **single-winner selector** — candidates register per `(domain, key)` and are ranked by a descending lexicographic tuple `(override_score, capability_score, priority, stack_level, registry_sequence)`. It answers *"which one?"*, always answerable, with no search and no unsatisfiable case. Comparable resolver packages in other ecosystems fall into different algorithm families (backtracking, SAT, ASP) that answer *"is there a solution?"*. This record prevents the comparison from being read as a roadmap.

- [ ] **Step 3: Write decision 1 — provider protocol, DEFERRED**

**Decision:** Do not adopt a pluggable provider protocol (the `resolvelib` `AbstractProvider` shape) for candidate sources.

**Rationale:** `CandidateSource` currently has four members — `local_pkg`, `remote_manifest`, `entry_point`, `manual` — and `CandidateRegistry` handles all four with a closed set of registration paths. A provider protocol earns its cost only when sources must be added *without* editing `oneiric/core/resolution.py`. With four known sources, the enum is cheaper and clearer than an abstraction.

**Reopen when:** `CandidateSource` gains a fifth member, **or** a source is required whose registration cannot be expressed by `register_candidate` / `register_pkg` (a marketplace, a policy server, a capability broker).

- [ ] **Step 4: Write decision 2 — joint/set resolution, DEFERRED**

**Decision:** Do not support resolving a *set* of components jointly, and do not introduce constraint solving, backtracking, or SAT-style resolution.

**Rationale:** The current model scores each `(domain, key)` independently and picks one winner. Set resolution needs a constraint system Oneiric does not have, plus machinery to explain an unsatisfiable assignment — a much larger surface than the one-winner model requires. Every selection Oneiric performs today (which adapter, which model, which pool, which action kit) is a single choice.

**Reopen when:** a concrete requirement appears for **mutually-compatible multi-component selection** — for example, a bundle whose adapters must agree on a protocol version, or a capability set where choosing one candidate excludes another. The trigger is a named requirement, not a preference for elegance.

- [ ] **Step 5: Write decision 3 — config interpolation for action kits, DEFERRED pending a security model**

**Decision:** Do not add `${...}`-style interpolation that lets configuration files invoke registered action kits.

**Rationale:** The registry this feature would need **already exists**. `ActionMetadata.to_candidate()` (`oneiric/actions/metadata.py:41`) converts every action kit into a resolver `Candidate` in `domain="action"`, keyed as `"compression.encode"`. Action kits are resolver candidates today; a separate OmegaConf-style resolver registry would duplicate the resolver rather than extend it.

The only missing piece is an interpolation *surface*. That surface is a security decision, not a feature decision, because `CandidateSource.REMOTE_MANIFEST` exists: a fetched remote manifest must not be able to invoke arbitrary registered callables. `docs/RESOLUTION_LAYER_SPEC.md` → Security & Integrity already states the governing rule: *"Do not auto-execute arbitrary code without digest verification."*

**Reopen when** all three of the following are decided:

1. Which sources may interpolate — at minimum, `REMOTE_MANIFEST` must be excluded.
2. Whether interpolation may invoke arbitrary registered callables, or only a restricted subset. `ActionMetadata` already carries `side_effect_free: bool` and `requires_secrets: bool` (`oneiric/actions/metadata.py:36`), which are the natural gating fields.
3. What the audit trail is — which calls were interpolated, from which source, with which arguments.

- [ ] **Step 6: Write decision 4 — priority sentinels, REJECTED**

**Decision:** Do not add `HIGHEST_PRECEDENCE` / `LOWEST_PRECEDENCE`-style sentinel values to `Candidate.priority`.

**Rationale:** `priority: int | None` already separates *unset* from *set* — an unset priority falls back to `ResolverSettings.default_priority` (`oneiric/core/resolution.py:120`). "Always last" is expressible as a very low integer. A sentinel buys type-safety against magic numbers, at the cost of two more public API values to document and test. The trade does not justify the surface.

- [ ] **Step 7: Write decision 5 — plugin position directives, REJECTED**

**Decision:** Do not add `tryfirst` / `trylast`-style positional directives.

**Rationale:** The numeric `priority` field already expresses position, and a second positioning mechanism creates ambiguity whenever both are set — the resolver would need a tiebreak rule between two mechanisms that mean the same thing.

**Explicitly not transferring:** the `pluggy` LIFO analogy does not apply. `pluggy` uses last-registered-first because it governs *hook execution* order, where a later-installed plugin must be able to override an earlier one. Oneiric's registry order governs *candidate selection*, where the same override semantics are already expressed by `priority`. Oneiric's own contract is **last registered wins** (`docs/RESOLUTION_LAYER_SPEC.md`, Precedence Rules tier 4) — coincidentally the same direction as `pluggy`, but for a different reason. Do not change it on the strength of the `pluggy` analogy.

- [ ] **Step 8: Write decision 6 — PubGrub-style conflict explanation, PARTIALLY ADOPTED**

**Decision:** Adopt the *explanation* half of conflict-driven resolution. Do not adopt the solver.

**Adopted:** reporting **why nothing won** — candidates excluded by capability filtering, with the capabilities they lacked. This is delivered by the `filtered` channel on `ResolutionExplanation` in Plan A, Task 3, and satisfies the spec's Observability requirement for a decision trace.

**Not adopted:** PubGrub's conflict *chain* machinery, which presupposes a constraint system over sets of candidates. That falls under decision 2.

**Rationale for the split:** Oneiric's `explain()` already answers *"why this one won"*; the gap was *"why nothing worked"*. Closing that gap requires reporting, not search.

- [ ] **Step 9: Write the Status and Trigger Summary sections**

Close the record with a table: decision, state (`deferred` / `rejected` / `partially adopted`), and the reopening trigger in one line each. Then a **Status** section reading `active`, dated 2026-10-29.

Run: `grep -nE "last registered wins|Explicit override|stack_level" docs/RESOLUTION_LAYER_SPEC.md`

### Task 2: Add the trigger detector

**Files:**
- Create: `tests/core/test_resolution_scope_triggers.py`

**Interfaces:**
- Consumes: `oneiric.core.resolution.CandidateSource` (a `StrEnum` with four members).
- Produces: no new API. A test module that fails when a deferred capability's precondition becomes true.

- [ ] **Step 1: Write the cardinality guard**

Create `tests/core/test_resolution_scope_triggers.py`:

```python
from __future__ import annotations

from oneiric.core.resolution import CandidateSource


def test_candidate_source_has_exactly_four_members() -> None:
    """Guard for ADR 0004 decision 1 (provider protocol deferred).

    A fifth CandidateSource means a new source kind must be pluggable without
    editing oneiric/core/resolution.py. Revisit the provider protocol then.
    """
    assert len(CandidateSource) == 4
```

The docstring is load-bearing: when this test fails, the failure message must tell the reader which decision to revisit.

- [ ] **Step 2: Write the companion assertion on member identity**

Add a second test in the same module asserting the exact member set, so a *rename* also trips the guard:

```python
def test_candidate_source_members_are_stable() -> None:
    assert {member.value for member in CandidateSource} == {
        "local_pkg",
        "remote_manifest",
        "entry_point",
        "manual",
    }
```

- [ ] **Step 3: Run the guard**

Run: `./.venv/bin/pytest tests/core/test_resolution_scope_triggers.py -v`

Expected: PASS (both tests — the enum currently has exactly four members).

- [ ] **Step 4: Verify the guard actually fires**

Temporarily add a fifth member to `CandidateSource` in `oneiric/core/resolution.py`, re-run the test, and confirm it FAILS. Revert the temporary edit immediately.

Run: `./.venv/bin/pytest tests/core/test_resolution_scope_triggers.py -v`

Expected while the temp member exists: FAIL. After reverting: PASS.

A guard that has never been observed to fail is not a guard.

#### Integration Contract

- **Triggered from**: The resolver test suite, on every run.
- **Returns to / updates**: Nothing. It reads `CandidateSource` and asserts its cardinality.
- **Demonstrable by**: `./.venv/bin/pytest tests/core/test_resolution_scope_triggers.py -v` — passes today; fails if a fifth source is added.
- **Rollback signal**: The guard fails spuriously — for example, if `CandidateSource` gains a member that is not a new *source kind* (a value that does not describe where candidates come from). In that case, amend ADR 0004 decision 1 rather than deleting the guard.
- **Observability added**: The deferred provider-protocol decision now surfaces automatically at test time instead of relying on someone remembering it.
